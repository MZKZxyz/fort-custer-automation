# Codex authentication decision — Sprint 6.11

Decision: **technical blocker; no subscription worker is activated.** The pinned
official CLI is 0.163.0. This is the objective's blocker deliverable, not an
executable live architecture or another orchestration layer. Zero live agents
can run. The future ceiling remains one. No credentials or billing were provisioned.

## A. Trusted subscription harness, external tools

The official client has real remote execution capabilities. In particular,
`codex exec-server --listen stdio://` is an executable, versioned transport;
experimental app-server `environment/add` can attach a WebSocket executor.
`--code-mode-host` moves code-mode evaluation to a remote host. Do not describe
these interfaces as nonexistent or assume they isolate every capability.

The stable schema generated by 0.163.0 omits `environment/add`; generating with
`--experimental` includes it. Neither an approval response nor a dynamic tool
callback is a replacement executor for all built-in tools. The code-mode host
delegates nested tools **back to the harness** (`CoreTurnHost::submit_tool`),
so moving that host alone does not move shell, filesystem and MCP execution.
Remote environment selection addresses execution environments; it does not
by itself prohibit local environments, local MCP subprocesses, hooks, plugins,
host filesystem client APIs or new tool registrations.

The exec-server is also not a grant authority. Its documented `process/start`
and filesystem RPCs accept optional caller-supplied sandbox contexts. Omitting
the context allows same-UID access. Its metadata labels are explicitly
correlation, not authorization. Directly exposing it to generated code, or
forwarding arbitrary RPCs from a harness, bypasses task scope and broker grants.
The real offline probe reproduces that read with synthetic controller policy
and authentication sentinels. Unknown RPC rejection is protocol validation,
not a permission check for a known powerful RPC.

There is also a concrete pinned-runtime sandbox blocker in the tested profile:
hosted Ubuntu's helper fails its permitted-file control with a loopback
`Operation not permitted` error and a panic while inspecting
`allowed.txt/.aws` (`Not a directory`). The nested cloud instead fails the
protected daemon-directory prerequisite. Neither environment demonstrates the
requested exact-file write profile. The diagnostic retains these observations;
it never converts setup failures into successful denied-access tests. These
findings concern the tested profile/platforms, not every possible VM sandbox.

**Blocking invariant:** this release cannot establish that every executable
capability crosses an immutable broker-controlled boundary, with no trusted-host
fallback. No documented stable universal interception contract was established
for the pinned interface. Experimental remote primitives are promising, but
their existence is insufficient evidence for that invariant. This is a scoped
support/security conclusion for this implementation, not a proof that every
future remote Codex topology is impossible. Do not patch Codex, invent OAuth
endpoints, treat prompt instructions as policy, or remove the gate to bridge it.

A future A implementation needs an official supported remote-only profile,
complete executable-tool/configuration inventory, explicit denial of every
unmediated route, grant-consuming receiver, independent watchdog and adversarial
tests on the target deployment. The probe here implements only the small
official executor diagnostic; it does not pretend to implement those services.

## B. Dedicated identity or disposable VM

Rejected for the required credential-confidentiality threat model. A separate
account protects the operator's credentials, but code running as the account
can read that account's own file-backed authentication storage. The real
exec-server subprocess `/bin/cat` and `fs/readFile` both read a synthetic 0600
`auth.json`. No real authentication file is examined. A VM containing both
Codex and its authentication has the same trust problem inside the guest.

Keychain storage can change storage mechanics; it is not evidence that arbitrary
same-user code cannot obtain credentials or use authenticated capabilities.
No keychain entitlement separation was tested or claimed. Subscription device
login/headless support does not solve this execution boundary. Do not copy a
personal login cache to a worker, and do not activate by logging in as fc-worker.

## C. Simplest supported alternative

Use the official **Responses API with application-executed function tools**:
the trusted controller holds a separately provisioned inference credential;
it sends approved source/instructions and exposes a small explicit function
schema. Generated function arguments are data. A fixed receiver validates each
call against the single-use grant and executes it in a credential-free VM.
Omit hosted shell/computer/browser, arbitrary MCP, code interpreter, web search,
and other executable tools. Reject unknown names/fields and policy overrides.
An API key is separate from a ChatGPT subscription and can incur API charges.

| Authority | Location and permitted use |
| --- | --- |
| Model inference credential | Trusted inference client only; never in tool env, files, responses or QA |
| Restricted worker transport credential | If required, narrow channel authorization only; no inference, host shell, VM management or publication authority |
| Execution privilege | Task-bound broker claim; receiver has only fixed VM channel and approved workspace capabilities |
| Publisher credential | Separate publisher identity and fresh human authorization; never on controller, coding or QA guest |

This is an alternative design, **not an API adapter implemented or enabled by
this PR**. The selected deliverable is the technical blocker, not three partial
live adapters. Preserve the existing API financial policy: provider usage limits
and project budgets must not be called hard $3/task or $10/day enforcement.
Absent authoritative financial guarantees/reconciliation, API activation also
remains blocked. The operator must separately choose/review API use and resolve
that requirement; no key creation, billing enrollment or fallback occurs here.
